# 发版规范

把本协作体系上传或更新到 GitHub 时适用：首次上传、日常推送、打版本号、写 Release 说明。日常改文件、提交单个改动不读本规范。

**传什么、不传什么以[仓库运行边界.md](../../仓库运行边界.md)为准**；本规范只写"怎么传"，不复述边界判断。

**执行顺序**：发版前检查 → 发版确认（**全程只问用户这一次**）→ 分组提交 → 推送并打标签 → 建 Release → 报告结论。

## 发版前检查（逐项做，任一不过不发）

1. **边界核对**：按[仓库运行边界.md](../../仓库运行边界.md)逐条核对本次要传的内容。用 `git status --short` 列出全部改动与新增路径，**新增的未跟踪路径逐个判断**——最容易漏的就是它们。
2. **密钥扫描**：对已跟踪文件扫真实密钥，命中的人工确认是占位符还是真值：

   ```text
   git grep -l -I -E "(sk-[A-Za-z0-9]{20,}|ghp_[A-Za-z0-9]{20,}|AKIA[0-9A-Z]{16}|BEGIN [A-Z ]*PRIVATE KEY|password\s*[:=]\s*[^\s]{8,})"
   ```

   框架自带的 `${DB_PASSWORD:}`、`REPLACE_WITH_NEW_RSA_*` 是占位符，放行。
3. **引用检查**：运行[检查引用.ps1](../AI协作体系维护/检查引用.ps1)（`powershell -File 检查引用.ps1`），要求**断链 0、绝对路径残留 0**。输出里"孤儿文件"集中在 `档案\` 下属于已知假阳性（档案按编号与关联经验检索，不靠引用），不处理。
4. **体量与同步**：确认没有单文件超过 100 MB（GitHub 硬限制）；`git rev-list --left-right --count origin/master...master` 形如 `0	0` 表示本地与远端一致。
5. **规则留痕**：本次若新增、修改或废弃了体系规则，对应[档案](../AI协作体系维护/档案/README.md)已新建或在原档案"后续变更"追加一行。只改知识内容、改错别字、调模板字段不算规则变更，不留痕。

## 发版确认（全程只问用户这一次）

检查通过后，**先把本次要发的东西整理成一份方案交用户确认**。用户点头后一路做到发版完成——分组提交、推送、打标签、建 Release 都不再逐步询问、不再重复确认内容。

方案用大白话写，不贴文件清单、不贴 diff，包含四块：

1. **本次改了什么**：按主题分组，每条一句话讲清"改了什么、为什么"；文件路径附在说明后面即可。
2. **本次确认不发的**：有哪些改动确认过不随仓库分发（被 `.gitignore` 排除的知识页正文、本地数据等），一句话交代，避免用户以为漏发。
3. **发版前检查结果**：一句话报断链、绝对路径残留、密钥扫描是否通过。
4. **版本号候选与 Release 要点**：给出候选版本号（格式 `v<主>.<次>.<修订>`）和这一版 Release 的标题与要点。

用户回答后：

- 说"行" → 按方案执行到发版完成。
- 要改内容 → 按用户意见调整后重新走本节确认，不自行跳过。
- 未回应版本号 → 不自行打号，等确认。
- 本机没有 `gh` 时，建 Release 需要用户手工粘贴一次：在方案里一并交代，届时只做粘贴这一步，不再重复确认内容。

## 提交

- **按主题分组提交，一组一个主题**，不把不相关改动糊成一个提交。
- 提交说明用中文，写清"改了什么、为什么"。
- 新增的档案文件跟它对应的规则改动进同一个提交，不单独发。

## 版本号

- 远端 `origin` 指向 GitHub，分支为 `master`。
- **版本号在「发版确认」那一次问里一起给出候选，不单独再问一次，也不自行打号。**
- 打标签：`git tag -a vX.Y.Z -m "<一句话说明这一版>"`，再 `git push origin vX.Y.Z`。

## 推送与 Release

1. `git push origin master`。
2. 推完核对：`git rev-list --left-right --count origin/master...master` 为 `0	0`，且 `git tag -l` 能看到新标签。
3. **Release 说明写给人看**：按「发版确认」里定下的标题与要点填；不贴文件清单，不贴 diff。
4. **建 Release 的方式**：先核查本机是否装有 `gh` CLI（`gh --version`）。有 → 用命令行建；没有 → 用 GitHub 网页建，把现成的标题和正文交给用户粘贴。安装 `gh` 只在用户明确要求时做。

## 发版后

- 向用户一句话报结论：发了哪个版本、包含哪几组改动、远端地址。
- 发版是**不可逆的公开暴露**：内容一旦推上 GitHub，本地删除后仍留在提交历史里。所以**发之前**的检查比发之后补救重要。
- 确实要撤回已公开的内容时，只能改写历史再强推，会破坏他人已克隆的副本；**先说明影响、取得用户确认再动**，不自行强推。

## 已知边界

- "某条内容该不该公开"由[仓库运行边界.md](../../仓库运行边界.md)判断，本规范不判。
- 本规范只管协作体自身这个仓库；项目仓库的 Git 流程不在本规范范围内。
