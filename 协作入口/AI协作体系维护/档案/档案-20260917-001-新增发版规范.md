## 结论

新增[发版规范](../../规范/发版规范.md)，把"把协作体系上传或更新到 GitHub"从每次临场摸索变成一条固定规则：发版前检查项、分组提交、版本号拍板方式、推送与 Release 做法、发版后的不可逆提醒。规则挂在[协作入口 README](../../README.md)的按需入口索引上，新窗口一读即知。

## 为什么

1. **规则缺口**：2026-09-17 实际要发版时全库检索"推送 / 打标签 / 版本号 / 发版"，`协作入口/` 下一条规则都没有。边界判断（靠根目录 `仓库运行边界.md`）、要不要分组提交、要不要打标签、Release 写什么，全是临场想的。换个新窗口再发一版，得从头摸一遍，摸出来的做法还可能和这次不一致。
2. **落点依据（关键）**：用户原意是"改根目录 `仓库运行边界.md`，让任何新窗口进来就知道怎么做"。但该文件全库只被根目录 `README.md` 引用一次——那是给人点的链接，**AI 新窗口不会读到**。AI 新窗口每次必读的是 `协作入口/README.md`（DSH 的 `AGENTS.md` 强制每次会话先读）。**规则写给 AI 看，就必须挂在 AI 真会读的那条链上**，否则等于贴在储藏室门上。
3. **与边界文件的分工**：`仓库运行边界.md` 继续只回答"传什么、不传什么"；本规范只回答"怎么传"，不复述边界判断（唯一权威）。两处互相指路，不互相抄写。
4. **用户同时决定**：`知识库/Wiki/` 下 59 个知识页正文**不随仓库分发**，只保留索引。此前该索引 59 条链接在新克隆里会是全断链（本地有、公开没有），故在索引开头补一句说明，避免使用者误判仓库损坏。

## 影响范围

- 新增 `协作入口/规范/发版规范.md`（发版前 5 项检查、分组提交、版本号由用户拍板、推送与 Release、发版后提醒、已知边界）。
- `协作入口/README.md`：按需入口索引新增一条触发条件（要把协作体系上传或更新到 GitHub 时读本规范）。
- `仓库运行边界.md`：「公开前重点」新增一条指路（本文件只管"传什么"，"怎么传"见发版规范）。
- `知识库/Wiki/index.md`：开头新增说明——本仓库只发布索引、不发布知识页正文，克隆后链接点不开属正常。

- 2026-09-17（同日追加）：补「发版确认（全程只问用户这一次）」节。用户要的效果是"在任何窗口说一句想上传 GitHub，它就知道怎么传、把本次改动讲给我、问我内容行不行，然后直接发上去"。原规范只有"AI 自己核对边界"（自己心里过一遍），**缺"讲给用户听并请其确认"这一步**；且版本号单列一条"报候选号等确认"，会与内容确认凑成问两次。故新增本节，把改动清单、不发清单、检查结果、版本号与 Release 要点打包成**一份方案、一次确认**；原「版本号」节改为指向本节，避免同一动作两处定义。另在开头补一行"执行顺序"，让新窗口一眼看到全程只有一个确认点。
