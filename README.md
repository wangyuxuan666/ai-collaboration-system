# AI 协作体系

让 AI 少占用你的时间，少浪费 Token，并且越合作越懂你的工作方式。

长期使用 AI，真正消耗人的往往不是某一次回答，而是这些重复发生的事情：每次都要重新解释背景和偏好；AI 读了大量无关内容，却没有抓住当前重点；复杂任务没人组织，角色之间互相等待或越界；做完一次之后，经验没有留下，下一次又从头开始。

这套协作体就是围绕这些痛点建立的。它把 AI 协作拆成入口、角色、流程、知识、记忆和工具，让一次任务不只是得到一个结果，还能减少下一次任务的沟通和试错成本。

## 它解决的痛点

### 重复解释：用长期记忆保留协作连续性

用户画像保存稳定的事实和全局偏好，经验保存特定场景下可复用的做法，项目和节点保存当前任务状态，知识库存放跨项目的客观知识。

它们各有位置，不把所有内容混成一份聊天记录。AI 可以在后续任务中复用已经验证过的协作方式，用户不必每次重新说明同一件事。

### Token 浪费：用入口树控制读取范围

AI 不需要把整个仓库一次读完。

它从协作入口进入，按任务逐层读取角色、专业领域、流程、参考资料、模板和工具。入口像树干，规则和专业内容是枝干，当前任务需要的文件才是末端的叶子；没有命中的内容不读取，也不会因为存在链接就无限展开。

“必读、按需、参考”分别承担不同职责，最小上下文让 Token 花在真正会改变当前判断的内容上。

### AI 只会回答：用角色和流程让它进入工作状态

一个角色不是一句“你现在是开发”或“你现在是产品经理”，而是一个完整岗位：有专业领域、职责边界、权限、免询问事项、工作流程、参考资料、交付模板和协作关系。

一个流程也不是任务清单，而是一条有轨道的线路：它规定进入条件、阶段产出、判断节点、交接对象、用户确认、返工路径和验收证据。

因此，使用时只需要告诉 AI：

> 你现在是产品经理，请接手这个需求。

AI 进入的是一套工作范围，而不是进行身份扮演。

### 复杂项目容易失控：用分工和验收把任务串起来

总控掌握项目目标、范围、节点、协作和最终验收，但不越界替专业角色做事；技术经理负责研发组织和技术落地；产品、UX、前后端、测试、部署和 Git 管理分别承接自己的工作。

在代码开发中，需求、UX、技术方案、研发组织、模块实现、测试、部署、Git 管理和最终验收之间通过任务包、交接记录和验收关系连接起来。没有交付物和验证证据，就不能把节点宣布为完成。

### 做完就遗忘：让经验回到下一次行动

经验不是任务总结，而是下一次遇到相似情况时能够改变判断或动作的记录。它需要经过实际使用和反馈，置信度才会变化；一次总结不会自动升级成永久规则。

当任务暴露出错误、重复、职责冲突或规则缺口时，问题还会被分流到正确的位置：该改规则就改规则，该沉淀经验就进经验库，该进入知识库就走知识库流程。

### 工具失效：让接入和恢复也成为体系的一部分

MCP 和 Skill 不只是工具名称的清单，还包括使用场景、平台适配、源码归属、权限边界、接入方式和验证方法。

工具不可用时，AI 先读取当前 Agent 的接入说明，优先恢复协作体内已有的源码或程序；只有确实需要外部安装、重启平台或更高权限时，才进入确认流程。接入完成后，还必须确认工具真实出现并通过实际调用验证。

## 这套体系如何组织

它更像一套分层的工作操作系统，而不是一个文件夹：

- **入口**负责把任务送进正确的分支；
- **角色**负责专业判断和职责边界；
- **流程**负责推进、交接、返工和验收；
- **知识库**负责收集、审核和复用客观知识；
- **自成长**负责用户画像、任务经验和长期记忆；
- **工具**负责把外部能力接入并保持可验证；
- **维护机制**负责检查重复、断链、冲突和规则缺口。

这些部分不是平行堆放的目录，而是通过入口、触发条件、引用关系、角色边界、交付关系和验收规则连接成一张可以运行的协作网络。

## 已经具体到什么程度

截至当前仓库，公开内容约 1770 个文件，其中包括：

- 56 个协作入口、规范和平台适配文件；
- 69 个专业角色与角色流程；
- 13 个可复用的角色模板；
- 1553 个代码开发框架、源码和参考文件；
- MCP、Skill、自成长记忆和可视化工作台等配套工具。

规模不是这套体系最重要的地方。重要的是这些内容已经被组织成可进入、可执行、可交接、可验收、可维护的结构。

## 如何使用

使用入口很简单：告诉 AI 你希望它承担的角色、要完成的任务，或需要解决的问题，并让它先读取仓库根目录 README 和协作入口。

例如：

> 你现在是项目经理，请接手这个项目，先梳理现状和下一步。

> 你现在是开发工程师，请先理解代码，再实现这个功能。

> 帮我整理这次任务中值得长期复用的经验。
