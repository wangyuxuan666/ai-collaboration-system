# 需求定义与交接

## 0. 开工前

- 按身份定位·价值观核对本次安排：用户立场、独立判断、需求可验证、克制充分、边界清晰。
- 任务涉及可复用专业结论时，按[知识库入口](../../../../../知识库/入口.md)检索；产品需求相关判断命中产品知识库（Wiki/产品）时读取对应知识页，未命中则跳过，不阻塞后续工作。

## 1. 理解需求与澄清

- 理解用户真正希望解决的问题、相关使用者和满意结果，区分表面要求与实际目标。
- 按[需求模糊冲突遗漏识别](../../../../../知识库/Wiki/产品/需求分析/知识/需求模糊冲突遗漏识别.md)检查：用户故事三要素是否齐全（角色/功能/目的）；是否存在模糊、冲突、遗漏、未验证假设。
- 澄清规则：影响结果且无法可靠判断时向用户追问；小问题按已有信息推进。发现更优方案、重要取舍或技术可行性风险时，向用户说明判断与影响，不悄然改变已确认的关键决定。
- 开展外部市场、同类产品或用户调研前，按核心文件"权限边界"的询问规则取得用户确认。

## 2. 定范围与优先级

- 与用户对齐"做什么 / 不做什么"，明确范围外事项。
- 按[需求优先级标注方法](../../../../../知识库/Wiki/产品/优先级/知识/需求优先级标注方法.md)为功能点标注优先级：P0（必须有，核心）/ P1（应该有）/ P2（可以有）；"不会有"不进本期范围。

## 3. 拆页面、写需求文档

- 按[页面清单与每页概要要素](../../../../../知识库/Wiki/产品/需求文档/知识/页面清单与每页概要要素.md)组织：先列页面清单（每页一句话职责），再写每页概要（用途/要求/重点细节/边界），最后写流程。
- 按[需求文档模板](../../../../模板/产品/产品经理/需求文档模板.md)形成文档，并按任务复杂度裁剪：简版（改动点+验收）/ 标准版（八大节从简）/ 全版（八大节完整）。
- 文档清楚表达研发需要理解和验收的内容：页面、规则、边界、状态、异常、验收依据；不写设计/技术细节；页面清单与每页概要只写业务职责与边界，信息架构、交互模型等体验结构由 UX 细化，不在需求文档展开。

## 4. 开发视角自检（成文后必做）

逐项核对，任一"否"则补齐后再交接：

- [ ] 页面清单齐了吗？开发知道做几个页面、每页是什么？
- [ ] 每页概要四要素（用途/要求/重点细节/边界）齐了吗？
- [ ] 流程写了吗？页面怎么串、用户怎么走完？
- [ ] 每条功能有优先级标注吗（P0/P1/P2）？
- [ ] 验收标准可测吗（Given-When-Then 或等价）？
- [ ] 用户核心诉求（原话级，尤其结构/体验类）都有对应可测验收项吗？
- [ ] 边界/异常/空态/失败情况有交代吗？
- [ ] 有没有混入设计/技术细节？有则删。
- [ ] UX 拿到这份文档，能直接开始信息架构和交互设计吗？

## 5. 反馈与交接

- **收口门槛**：页面结构/栏目定了 ≠ 需求完成——各屏/各栏目的内容与文案原稿须**逐项与用户对完并确认**（文案以用户原稿为准）后，才可宣布需求文档完成并反馈收口；未确认项明确列出、继续与用户对完，不提前收口回传。
- 完成需求文档和必要的技术影响分析后，先向用户反馈结果。
- 获得用户同意后，将文档和必要上下文提交总控；总控负责规划后续研发协作。未获同意时，不跨对话框提交或推进。
- 技术可行性判断由技术角色负责；需要联系技术角色时，按[代码开发专业领域](../专业领域/代码开发.md)的技术协作规则取得确认。
