# 代码开发流程

本流程用于总控规划并推进**从零新建**或**修改已有**的代码项目。各环节标注归属角色与专业领域；总控按阶段判断并创建专业负责人窗口（如技术经理），研发线内下级窗口由技术经理按角色文件"下级窗口组织"创建，总控不规定研发线内部角色与数量。所有角色窗口都必须可定位、绑定对应角色并收到任务包。

**角色 = 角色 + 专业领域**：创建角色窗口时，按[节点模板](../../../../模板/项目治理/总控/节点模板.md)填写“当前专业领域”；**填写了即按该领域加载对应专业领域文件，不填写即默认普通角色**（不加载任何专业领域）。新窗口中的 AI 据此读取对应文件，不猜测。

**串行原则**：页面敲定 → 接口设计 → 开发。大阶段串行，每一步的输入是上一步的产出；研发阶段按功能模块逐块闭环，同一模块内前后端按接口契约协作，上一模块测试通过后再开始下一模块。

## 0. 启用判断（【总控】先做，决定从哪开始）

### 0.0 项目启动语义

用户说“开始搭建”“开始做”“着手开发”等表达时，进入**流程规划态**：先判断项目是否从零、核对已有输入、确定阶段与角色窗口，不直接执行开发或修改代码。规划态必须产出项目方案、角色窗口计划、首个交付物和验收标准；用户确认后，才创建对应新窗口并绑定角色执行。只有用户明确授权“按方案执行”“开始写代码”或等价表达，才可进入代码修改。

本流程是详细流程，不是死流程。总控接手"代码开发项目"后，先核对已有输入，**从已有成果处切入，跳过已完成环节，缺什么补什么**：

- 项目完全从零（无需求、无代码、无页面）→ 从第 1 节开始完整走。
- 已有项目 / 需要修改现有代码 → 先走第 0.1 节"理解现状"，再按改动范围决定切入环节。
- 已有已确认需求文档 → 跳过第 2 节。
- 已有技术栈与仓库 → 跳过第 3 节对应部分。
- 已有代码框架与页面（含 UI 基线）→ 跳过第 4 节，从接口设计或直接开发切入。
- 已有接口文档 → 跳过第 5 节，直接进入开发。
- 小范围改动（如加一个接口、改一个页面、修 Bug）→ 不机械套用全部环节；按影响范围直接安排对应节点，能一步完成的不拆阶段。

判断原则：已有成果可复用则不复做；只有影响结果的缺口才补；**拿不准从哪开始或现有成果是否可用时，向用户确认**，不自行假设。

### 0.1 理解现状（仅已有项目 / 修改场景）

- 【总控】先用 UA（skill，用法见[第 10 节](#10-工具使用说明按需读取卡住才读)）分析项目业务全貌（业务域、业务流程、文件摘要），快速理解"这项目是干嘛的"；再用 CodeGraph 建图（如项目根无 `.codegraph\` 则 `codegraph init`）并查询改动影响（`codegraph impact` / `explore`），评估爆炸半径。
- 目的：接手或修改前先摸清现状，避免凭猜测规划；分析结论记入技术文档（第 3 节滚动记录）或项目协作目录。

### 0.2 改动规模分级（决定角色窗口裁剪）

按改动影响决定角色窗口数量，能少就少（最小充分，省 token）：

| 规模 | 判定依据 | 角色窗口 |
|---|---|---|
| 轻量 | 改单个页面样式/单个接口实现/修 Bug，不动需求、不改接口契约、不改 UI 结构 | 总控 → 对应执行角色（前端开发/后端开发）直接改；按角色成功指标自检 + 节点回报验收，不建产品/UX/测试等多余窗口 |
| 标准 | 新增模块/多页面功能；涉及需求或 UI 结构变化 | 按需裁剪走全流程：需求（产品经理）→ 技术准备（技术经理）→ UX/前端 UI 方向（有 UI 变化时）→ 接口 → 开发 → 测试（按风险决定）→ 部署 |
| 完整 | 从零项目/大重构/跨端接口大改 | 全流程，按第 1~9 节执行 |

判定原则：不涉及需求、接口契约或 UI 结构变化的改动走轻量；拿不准走哪个规模时，向用户确认，不自行假设。注意：新增接口会改接口契约，属标准级以上，不走轻量。

## 1. 项目初始化（【总控】）（已有 AI协作/ 可跳过）

- 【总控】确定项目根目录，在项目根创建 `AI协作/` 目录结构（按[项目协作目录模板](../../../../模板/项目治理/项目协作目录模板.md)）：`项目协作目录.md`、`节点/`、`方案/`、`交付/`。
- 目的：先搭好结构，后续每个角色都从项目协作目录定位自己的文档存放处（技术文档、接口文档、节点、交付记录），不各放各的。

## 2. 需求阶段（【产品经理】主导，【总控】衔接）（已有已确认需求文档可跳过）

- 【总控】创建产品经理新窗口并绑定“产品经理”角色，按[节点模板](../../../../模板/项目治理/总控/节点模板.md)准备任务包；任务包必须写明“先向用户提问并共创需求，产出需求文档”，需求文档存放位置写入“文档存放位置”字段（默认 `AI协作/方案/需求文档.md`，以总控指定为准）。
- 【产品经理】第一项动作必须是向用户提问并收集回答；未获得用户回答前，只能整理问题和需求草案，禁止自行定稿或创建正式需求文档。需求文档完成后必须交用户确认，再反馈给总控。
- 【总控】确认需求文档已满足规划所需，转交技术经理。

## 3. 技术准备（【技术经理】主导，建库由技术经理组织承接）（已有技术栈与仓库可跳过对应部分）

- 【总控】创建技术经理新窗口并绑定“技术经理”角色，按[节点模板](../../../../模板/项目治理/总控/节点模板.md)建立任务文件（任务包引用本流程第 3 节；"文档存放位置"填技术方案总文档路径，见下）。
- 【技术经理】判断本次用什么技术栈（语言、框架、数据库、部署方式等），形成初步技术方向；**技术栈受用户约束（如用户指定、已有技术栈、团队熟悉度）影响时，先确认再定**，不自行假设。
- 【技术经理】框架选型：读[框架总览](../../../../../代码开发/开发框架使用/框架总览.md)（框架模板库入口），按判断规则初步定 1~2 套候选；需要时深看对应框架说明书；**向客户推荐并说明理由（"推荐选 X，理由是……"），客户拍板后定框架**，不自行决定；两套都不合适时向总控/客户说明，另选。选型结论记入技术方案总文档"技术栈决策"章节。
- 【技术经理】把建仓所需的技术要求（仓库名、可见性、首次拉取目录等）写入技术方案总文档并经用户确认；技术方案与窗口安排获用户确认后，由【技术经理】创建建仓窗口并下发任务（承接角色由技术经理按"下级窗口组织"确定，本流程不点名具体角色）。
- 承接建仓任务的窗口按[Gitee 仓库创建与目录登记](../../../../../角色/角色列表/软件研发/Git 管理员/流程/Gitee 仓库创建与目录登记.md)创建仓库、登记目录并完成首次本地拉取，项目根就绪。
- 【技术经理】按[技术方案总文档模板](../../../../模板/软件研发/技术管理/技术经理/技术方案总文档模板.md)**滚动记录**技术文档（存放位置按[代码开发专业领域](../专业领域/代码开发.md)默认文件结构，以总控任务包指定为准）：技术栈决策、项目与仓库等；后续每个环节完成后同步更新对应章节，保持全程最新。接口契约与数据模型在独立[接口文档](../../../../模板/软件研发/技术管理/技术经理/接口文档模板.md)中维护，不在技术文档重复。

## 4. 框架搭建、UX 设计与 UI（研发窗口由技术经理按"下级窗口组织"组织；UX 方案须经用户确认）（已有框架与页面可跳过）

- 【技术经理】按角色文件"下级窗口组织"的开工门槛创建研发所需下级窗口：先读完需求与方案文档、把影响安排的问题向用户问清、再将研发所需的角色与窗口安排及拟推进流程交用户确认并记录结论，用户确认后才创建，按[节点模板](../../../../模板/项目治理/总控/节点模板.md)分别建立任务文件；本流程不规定研发线内部角色与数量——下文出现的"前端开发/后端开发/UI 方向"等均为研发执行角色示例，实际角色与数量以技术经理与用户确认后的安排为准。窗口增减由技术经理自定并登记协作目录。
- 研发窗口的方向与专业领域（如框架搭建、UI 实现、业务开发等，以项目当时需要为准）由【技术经理】按"下级窗口组织"确定并下发相应任务包；执行中超出其职责范围或需独立验证、上线收口时回传总控。
- **框架来源**：搭框架按技术方案总文档"技术栈决策"章节**选定的框架**执行（第 3 节技术经理选型结果）；框架模板从[开发框架使用](../../../../../代码开发/开发框架使用/框架总览.md)落地——复制对应框架的 `前端\`、`后端\` 目录到项目根（框架级选型说明见该框架目录的 `框架说明书.md`，复制后按前端/后端目录内各自的 `开发说明书.md` 操作）；未从模板库选框架时按官方文档从零搭。
- 【前端负责人】组织前端开发（框架方向）搭框架；【后端负责人】组织后端开发（框架方向）搭框架；代码落在项目根，**前后端框架均完成并提交 Git 基线后**，做工具接入。
- 【技术经理】协调整体架构与跨端接口，不逐项盯执行。
- 【总控】需求文档确认后，创建 UX 新窗口并绑定"UX"角色，按[节点模板](../../../../模板/项目治理/总控/节点模板.md)建立任务文件（输入：已确认的需求文档；UX 交付物默认放 `AI协作/方案/UX/`，以任务包"文档存放位置"为准），产出**UX 方案与设计契约**（信息架构、交互模型、页面结构、状态设计），形态为**低保真逻辑轮廓/原型**（线框/示意图，HTML/SVG，浏览器可打开），只表达"怎么用"，不承担视觉样式；**"怎么用"的确认关口 = 看 UX 轮廓原型**，不得仅凭文字契约拍板；**UX 方案必须经用户确认（有确认记录）后，前端 UI 方向才可产出静态代码**；视觉样式与最终版效果（色板、组件外观、质感、动效）由前端 UI 方向负责，UI 方向用 UIUXProMax 出风格候选、**最终视觉方向由用户拍板**，"长什么样"的确认关口 = 先经风格方向确认（UI 方向用 UIUXProMax 出候选、用户选一套，见[界面实现流程](../../../../../角色/角色列表/软件研发/开发/前端/前端开发/流程/界面实现.md)第 2 节），再看 UI 真实页面；UX 设计与框架搭建并行，互不阻塞。
- 【技术经理】按"下级窗口组织"门槛创建 UI 实现窗口（专业领域：UI 方向），发送产出 UI 静态代码的任务包并建立任务文件。
- 【前端负责人】框架可用且 UX 方案经用户确认后，组织前端开发（UI 方向）**按已确认的 UX 方案**，按[界面实现流程](../../../../../角色/角色列表/软件研发/开发/前端/前端开发/流程/界面实现.md)产出**前端静态代码**（页面结构、样式、交互骨架，非设计图），带用户确认并敲定页面，形成 UI 基线并**提交 Git**（作为业务方向的输入基线）。**页面敲定是本流程的关键节点**。
  - **用户确认门槛**：UI 静态代码必须经用户确认通过（有确认记录，如页面清单与确认结论）后，才能返给技术经理进入接口设计；未经用户确认不得向下流转。
  - UI 静态代码敲定后，UI 方向**转为待命**（窗口保留，不主动推进后续开发）；后续页面或视觉有修改时，仍由 UI 方向按[界面实现流程](../../../../../角色/角色列表/软件研发/开发/前端/前端开发/流程/界面实现.md)处理，不归业务方向改。
- **工具接入（前后端框架均完成后，由【技术经理】执行一次）**：
  - 用 lrnev 初始化项目治理（记录 Scene/项目结构），贯穿后续全程。
  - 用 codegraph init 建立代码图谱，作为首个代码基线；后续开发用它查调用关系。
- **业务体检（新建项目，用 UA）**：框架 + 首批功能落地后，总控用 UA（skill，用法见[第 10 节](#10-工具使用说明按需读取卡住才读)）扫一次代码，核对"实际实现与需求的业务理解是否一致"；开发中后期模块增多后再扫一次，检查业务结构是否清晰。发现问题按偏差处理，不阻塞主流程。
- **串行空窗（有意设计）**：UI 敲定前，后端在框架完成后不开始接口相关开发，等待接口文档；此空窗是串行原则的代价，宁等不返工。后端可趁机完善框架基础能力，但不做可能随页面变化返工的数据或接口设计。

## 5. 接口文档设计（【技术经理】列清单 → 【后端负责人】细化）（已有接口文档可跳过）

- 【技术经理】从已敲定的页面和功能点推导**接口清单**（有哪些接口、每个接口的边界、调用方与提供方），先建接口文档文件、写入清单；页面结构以 UX 方案为准。
- 【技术经理】根据接口清单、页面和数据依赖，把研发拆成**可独立验收的功能模块**（一个模块 = 一组可独立交付的接口及其页面功能，不按前后端工种拆成两条流水线），拆定前与前后端负责人对齐一次，确认后写入项目协作目录的"代码开发模块进度"；同时形成测试范围和重点建议，一次性回传总控。
- 【后端负责人】细化接口前用 codegraph explore 查现有代码调用关系，确认新接口与既有模块的交互边界；接口文档存放按[代码开发专业领域](../专业领域/代码开发.md)默认文件结构（`AI协作/方案/接口文档.md`），以总控任务包指定为准，作为前后端开发的共同依据。
- 【后端负责人】按技术经理已拆定的模块分组，先定**数据模型**（实体、字段、关系），再按清单细化**接口文档**（字段、入参出参、错误处理、鉴权与访问约束），按[接口文档模板](../../../../模板/软件研发/技术管理/技术经理/接口文档模板.md)在同一文件继续完善，使前端后端都能看懂；不自行改模块划分，发现模块边界与接口分组对不上时，回技术经理对齐后再细化。
- 【总控】确认模块拆分和测试建议。需要独立测试时，在首个模块开发前创建一个测试工程师窗口，**任务包必须写明研发对接人 = 技术经理及其窗口 ID**，并登记进项目协作目录"窗口目录"；明确测试范围、技术经理为研发对接人和模块测试结果回传方式（模块测试记录 → 技术经理，见测试结论模板）；后续普通模块测试不再逐次经过总控。其他角色窗口需与技术经理等协作对象对接时同理：创建窗口的任务包写明对接人及其窗口 ID 并登记窗口目录，避免协作对象间互找不着。

## 6. 后端开发（【后端开发·业务方向】执行，【后端负责人】审查）

- 【技术经理】在首个模块开始前创建后端开发窗口（专业领域：业务方向）并发送任务包；【后端开发】按接口文档实现当前模块的后端接口。
- 每完成一个模块：【后端负责人】检查契约符合性与可靠性，没问题后交接给前端开发；发现错当场责令对应后端开发窗口修改并复核，不流到下一层。
- **工具使用（【后端负责人】）**：
  - lrnev：每个模块开始前建 Task（记录模块任务），模块完成后 task_update(completed)，作为进度账本贯穿全程。
  - CodeGraph：模块完成后用 codegraph impact 查该模块改动的影响面，确认未破坏既有调用。

## 7. 前端开发（【前端开发·业务方向】执行，【前端负责人】审查）

- 【技术经理】在首个模块开始前同步创建前端开发窗口（专业领域：业务方向），发送任务包并建立任务文件；【前端开发（业务方向）】拿已敲定的前端静态代码，按接口文档完成当前模块的前端逻辑和联调。
- **模块闭环（串行）**：同一模块的前后端可按稳定契约协作，但前后端都不得在当前模块测试通过前正式开始下一模块。
- 每完成一个模块：【前端负责人】检查对接正确、符合契约，没问题后向技术经理报告该模块通过本领域验收（技术经理负责更新模块进度表）；发现错当场责令对应前端开发窗口修改并复核。
- 业务方向只对接已有静态代码和接口文档，不直接改 UI；页面或视觉需要调整时，由【前端开发（UI 方向）】按[界面实现流程](../../../../../角色/角色列表/软件研发/开发/前端/前端开发/流程/界面实现.md)处理。
- **修改场景变体**：修改已有项目且无现成静态代码（旧项目未走 UI 基线流程）时，前端业务方向直接在现有代码上按接口文档开发，不依赖静态代码基线。

## 8. 模块闭环与整体检查（【技术经理】主导）

- 【技术经理】一次只推进一个未通过测试的模块，并在模块进度表中记录负责人、验收标准和当前状态；**模块进度表（项目协作目录"代码开发模块进度"）仅由技术经理更新**，其他角色只报告结论，不直接改表。
- 【前后端开发】完成当前模块并自检；【前后端负责人】分别验收本领域实现；【技术经理】再核对跨端契约、整体技术行为和交付证据。
- 总控已创建测试窗口时，【技术经理】把通过技术验收的当前模块交给【测试工程师】独立验证。Bug 修复按[研发组织与分工](../../../软件研发/技术管理/技术经理/流程/研发组织与分工.md#模块闭环)执行；复测通过后才关闭当前模块并开始下一模块。
- 总控已决定该项目不需要独立测试时，模块技术验收通过后可关闭当前模块；免测依据由总控记录，不由技术经理自行决定。
- 全部模块关闭后，由总控将项目状态记为“研发自检完成”。【技术经理】用 codegraph impact 核对跨端调用关系、用 lrnev report 核对进度与治理欠账，完成整体技术验收，写入 `AI协作/交付/研发技术交接记录.md` 并回传总控；由总控将项目状态更新为“整体技术验收完成”。
- 正式开发后的用户沟通按[角色通用规则](../../../../规范/角色通用规则.md)执行。
- 节点 token 控制按[节点模板](../../../../模板/项目治理/总控/节点模板.md)中的“尝试预算”和“提前停止依据”执行。

## 9. 最终回归测试与部署（【总控】收口，【测试工程师】【部署工程师】执行）

- 已有测试窗口时，【总控】在研发整体交接后安排跨模块关键路径和必要回归测试，项目状态更新为"待测试"；不重复逐项重测已经通过的模块。无既有测试窗口而需要回归测试时，总控先创建测试工程师窗口再安排。
- 【测试工程师】按[测试流程](../../../../../角色/角色列表/软件研发/测试/测试工程师/流程/测试流程.md)输出最终回归测试结论并回传总控；由总控将项目状态更新为“测试完成”。
- 最终回归测试发现 Bug 时，按[研发组织与分工](../../../软件研发/技术管理/技术经理/流程/研发组织与分工.md#模块闭环)执行修复和复测。
- 【总控】测试通过后进入"总控最终验收"；无独立测试窗口时，在技术经理整体交接后记录免测依据并直接进入"总控最终验收"。总控按上线前核对项逐项核对（见下，默认不放行，证据齐了才放行），创建部署工程师窗口；【部署工程师】按[部署与发布](../../../../../角色/角色列表/软件研发/部署/部署工程师/流程/部署与发布.md)与用户直接沟通部署方案（部署到哪、域名与费用、资源准备与访问方式等，用户在部署窗口确认方案），确认后才执行部署与运行验证，按部署交付记录留痕；部署阶段用户沟通在部署窗口内直接进行，不经总控转述。
  - 上线前核对项（端到端旅程、跨设备、性能基线、安全、验收逐点对照）以[代码开发验证核对表](../../../../模板/项目治理/代码开发验证核对表模板.md)"总控"列 + "上线前/整体"环节行为准，不在此重复；核对时结合测试结论与联调记录、按知识库性能与安全规范逐项核对，未达标按未达标处理上报，不静默放行。免测项目无测试结论时，端到端与验收核对依据改用研发自检证据与研发技术交接记录。
  - 核对结论写入总控自身的最终验收记录，不改写技术经理的研发技术交接记录。

### 研发至验收状态约束

`研发实现中 → 研发自检完成 → 整体技术验收完成 → 待测试 → 测试完成 → 总控最终验收`

- 项目研发开始或返工时为“研发实现中”；全部模块完成闭环后为“研发自检完成”。
- 只有技术经理完成整体技术验收并向总控提交交接结论，才能进入“整体技术验收完成”。
- 只有总控安排最终回归测试，才能进入“待测试”；模块测试期间项目仍为“研发实现中”。
- 总控决定不需要独立测试时，记录依据后可从“整体技术验收完成”直接进入“总控最终验收”。
- 最终回归测试发现需返工的问题时，项目状态回到“研发实现中”，由技术经理组织原开发窗口修复；涉及目标、范围、验收标准、重大风险或新增窗口时由总控决定。

### 单模块状态约束

`开发中 → 模块自检完成 → 模块技术验收通过 → 模块测试中 → 待修复 / 待复测 → 模块通过`

- 当前模块未到“模块通过”前，不正式开始下一模块。
- Bug 修复按[研发组织与分工](../../../软件研发/技术管理/技术经理/流程/研发组织与分工.md#模块闭环)执行。

## 10. 工具使用说明（按需读取，卡住才读）

本流程涉及的辅助工具：**UA**（skill：用时先 read `工具\skills\README.md` UA 场景表；业务理解，已有项目场景）、**CodeGraph**（代码图谱）、**lrnev**（项目治理）。

- **UA**（skill：用时先 read `工具\skills\README.md` UA 场景表）：已有项目 / 接手场景，分析项目业务全貌（见第 0.1 节）。
- **lrnev**：项目级治理（Scene / Spec / Task / 进度），贯穿开发全程；数据存在项目根 `.lrnev\`。
- **CodeGraph**：代码图谱，回答"X 在哪、谁调用了 X、改 X 影响什么"；数据存在项目根 `.codegraph\`。
- **触发原则**：只有影响面无法凭经验判断的改动才用 CodeGraph；简单局部修改不用，不为用工具而用。

### 工具不可用时的排查链

1. 项目根有 `.codegraph\`？有 → 直接用；没有 → `codegraph init`。
2. `codegraph init` 失败 → 检查 `codegraph --version` 能否运行：
   - 能运行 → 检查当前 agent 是否注册了 codegraph MCP（Codex 用 `codegraph install` 或查 `~/.codex/config.toml`；DSH 手动改 `cordis.patch.yml` 的 `insert:` 块）；已注册仍不行 → 重启 agent 后重试。
   - 不能运行 → 向用户说明来源与影响，取得同意后 `npm i -g @colbymchenry/codegraph`。
3. lrnev 不可用同理：先查项目根 `.lrnev\` 与 `lrnev --version`，未装则取得用户同意后 `npm i -g lrnev`，再按对应 agent 的 MCP 接入流程注册。
4. UA 不可用：查协作体 `工具/skills/代码开发协作工具/Understand-Anything/` 仓库是否存在：
   - 仓库不在 → 引导用户 clone（来源 `https://github.com/Egonex-AI/Understand-Anything.git`，说明位置与影响，征得同意后执行）。
   - 仓库在 → 按 UA 场景表 read 对应 `understand-*/SKILL.md` 确认可读；读不到或步骤执行失败 → 说明卡在哪一步，按 `工具/skills/README.md` 的环境要求准备（Node ≥ 22 / pnpm）。
   - 仍不可用 → 按本平台 [skills接入.md](../../../../../协作入口/Agent适配/README.md) 处理；不可用时仍可按现有方式（人工梳理 + 文档阅读）理解项目，不阻塞流程。
